What is GraphQL?

  • GraphQL is a query language for APIs and a runtime for fulfilling those queries with your existing data
  • Provides a complete and understandable description of the data in your API
  • Gives clients the power to ask for exactly what they need and nothing more
  • Makes it easier to evolve APIs over time
  • Enables powerful developer tools

the pitch, in six points

Why GraphQL?

  • No Over-fetching — get only the fields you need
  • No Under-fetching — get related data in one request
  • Strongly Typed — schema defines what's possible
  • Introspection — clients can discover API capabilities
  • Developer Experience — excellent tooling (Apollo Studio, GraphiQL)
  • Evolutionary — add fields without breaking existing queries

Defining a Schema

Query

type Query {
  users(limit: Int): [User!]!
  user(id: ID!): User
  me: User
}

Mutation

type Mutation {
  register(input: CreateUserInput!): AuthResult!
  createPost(...): Post!
  deletePost(id: ID!): Boolean!
}

Subscription

type Subscription {
  postCreated: Post!
  postUpdated(id: ID!): Post!
  commentAdded(...): Comment!
}
Query defines reads, Mutation defines writes, Subscription defines real-time events — every operation your API supports must appear in one of these three root types.

Resolvers: The 4 Parameters

Resolvers are functions that return values for fields:

resolvers.js
const resolvers = {
  Query: {
    user: (parent, args, context, info) => {
      // parent: result from parent resolver
      // args: { id: "1" } - field arguments
      // context: shared data (user, db, pubsub)
      // info: query metadata (rarely used)
      return context.db.getUserById(args.id);
    }
  }
};

Resolvers can nest per-field

const resolvers = {
  Query: {
    users: (_, { limit, offset }, ctx) =>

  User: {
    // Nested resolver for User.posts field
    posts: (parent, _, ctx) =>
      ctx.db.getPostsByAuthor(parent.id),
  },
};

Cursor-Based Pagination

reeltalk-api/src/resolvers/index.js
connection.graphql
type MovieConnection {
  edges: [MovieEdge!]!
  pageInfo: PageInfo!
}
type MovieEdge { cursor: String! node: Movie! }
type PageInfo {
  hasNextPage: Boolean!
  endCursor: String
}

query {
  movies(first: 6, after: "m6") {
    edges { cursor node { title } }
    pageInfo { hasNextPage endCursor }
  }
}
Cursors are more robust than offset/limit — inserting or deleting items elsewhere in the list doesn't shift everyone else's pagination.

The N+1 Problem

reeltalk-api/src/resolvers/reviewStatsLoader.js

A naive resolver for a relationship field often queries once per parent — 20 movies = 1 query for the list + 20 queries for reviews:

reviewStats.js
Movie: {
  reviewStats: (movie) => { // ❌ runs once PER movie
    const movieReviews = reviews.filter(r => r.movieId === movie.id);
    return computeStats(movieReviews); // 20 movies = 20 lookups
  }
}
This is invisible in a query returning one movie. It only shows up once you fetch a list — exactly why it's easy to miss in development and painful in production.

Precise Cache Updates (cache.modify)

reeltalk/src/cache/appendReview.js

cache.modify surgically updates just the affected fields, instead of re-fetching everything via refetchQueries:

appendReview.js
const [createReview] = useMutation(CREATE_REVIEW, {
  update(cache, { data }) {
    cache.modify({
      id: cache.identify({ __typename: 'Movie', id: data.createReview.movieId }),
      fields: { reviews(existingRefs = []) {
        const newRef = cache.writeFragment({ data: data.createReview, fragment: REVIEW_FRAGMENT });
        return [...existingRefs, newRef];
      } },
    });
  },
});
⚠️ Field modifiers run in normalized-store order, not the order you write them. Resolve shared logic with a separate cache.readFragment call first.
