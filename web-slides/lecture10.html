RESTful API Design

  • REpresentational State Transfer — a set of rules developers follow when building an API
  • A software architecture style for building scalable web services
  • REST is independent of any underlying protocol — not necessarily tied to HTTP
  • Stateless: no client context is stored on the server between requests
A REST API is simply an Application Programming Interface that follows REST's principles.

representation.md
lecture10 / representation
nouns, not verbs

Representation

  • A resource can be represented in different ways — but a representation must refer to a unique resource
  • URIs need not have structure, but a consistent structure helps clients navigate (see api.github.com)
✅ noun — identifies a resource
good
http://example.com/articles/1
❌ verb — describes an action
avoid
http://example.com/articles/1/delete
The HTTP method already says what to do (DELETE /articles/1) — the URI just says what it's doing it to.

Uniform Interface

  • Resource-based: resources are identified by URIs
  • Manipulation of resources through representations
  • Self-descriptive messages
  • Hypermedia as the Engine of Application State — HATEOAS
    • Clients deliver state via body, query-string params, headers, and the requested URI
    • Servers deliver state via body, response codes, and response headers
    • Links are used to navigate between resources

Common Beginner Mistakes

  • Using verbs in the URI — /getBooks
  • Always returning 200, even for errors
  • Forgetting express.json()
  • Comparing a string id with a number id
  • Mixing query params and body without reason
  • Returning inconsistent JSON shapes
Keep the API predictable. Every one of these mistakes makes the frontend's job harder to reason about.

REST API Design

  • 1. Figure out the data set
  • 2. Break it into resources
  • 3. Design the URIs
  • a. name the resources with URIs
  • b. expose a subset of the uniform interface (CRUD)
  • c. design the data in JSON
  • d. configure representation accepted from / served to clients
  • e. error handling with status codes

Disadvantages of REST

  • No standard
  • No official documentation
  • Not all resources fit the REST model — login, logout, etc.
  • Status codes need to be unified across a team
  • 404 is ambiguous — is the interface not discoverable, or is the resource just not available?

Suggestions When Designing a REST API

  • Use plural nouns instead of verbs
  • Use HTTP verbs, but you don't need to use all of them
  • Use sub-resources for relations (e.g. /users/:id/orders)
  • A 100% RESTful API? Impossible! Aim for consistency, not purity.

Consistent Error Response Format

Always return errors in a consistent JSON shape — this makes frontend error handling predictable.

error-handler.js
// ✅ Good: consistent error format
app.use((err, req, res, next) => {
  res.status(err.status || 500).json({ success: false,
    error: { message: err.message, code: err.code || 'INTERNAL_ERROR' } });
});
app.get('/api/users/:id', async (req, res, next) => {
  const user = await User.findById(req.params.id);
  if (!user) {
    const err = new Error('User not found');
    err.status = 404; err.code = 'USER_NOT_FOUND';
    return next(err);
  }
  res.json({ success: true, data: user });
});

API Versioning

As your API evolves, you need a strategy to avoid breaking existing clients.

versioning.js
// URL versioning (most common)
app.use('/api/v1/users', usersRouterV1);
app.use('/api/v2/users', usersRouterV2);

// Header versioning
app.use('/api/users', (req, res, next) => {
  const version = req.headers['api-version'] || '1';
  // route to the appropriate handler
});
For this course, URL versioning (/api/v1/...) is sufficient. Just know the alternatives exist.
