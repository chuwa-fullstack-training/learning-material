ACID: Atomicity

"All or nothing" — a transaction completes fully, or not at all.

bank-transfer.sql
await client.query('BEGIN');

await client.query('UPDATE accounts SET balance = balance - 100 WHERE id = 1');
await client.query('UPDATE accounts SET balance = balance + 100 WHERE id = 2');
// ⚡ power failure here? Neither UPDATE is saved yet.

await client.query('COMMIT'); // only now are BOTH changes saved
If the power fails before COMMIT, the whole transaction rolls back — money is never deducted from one account without appearing in the other.

ACID: Consistency

Data always moves from one valid state to another valid state.

constraints.sql
-- Constraints enforce consistency
CREATE TABLE accounts (
  id SERIAL PRIMARY KEY,
  balance DECIMAL(10,2) CHECK (balance >= 0), -- no negative balances!
  user_id INTEGER REFERENCES users(id)          -- must reference a valid user
);

-- This will FAIL (constraint violation)
UPDATE accounts SET balance = -50 WHERE id = 1;
-- ERROR: violates check constraint "accounts_balance_check"

Concurrent transactions don't interfere with each other.

Committed transactions survive system failures.

After COMMIT returns: data is on disk, not just in memory. It survives power loss, crashes, and restarts — and can be recovered from the transaction log.

lecture09 / evolution-of-mongodb

Evolution of MongoDB

  • Initial NoSQL databases mostly supported read-only-style operations
  • Not originally great at high-volume transactional workloads
  • MongoDB 4.0 added multi-document ACID transactions
  • Also evolved: foreign-key-style references (alongside embedding), schema validation, aggregation pipelines, indexes
The "NoSQL means no rules" stereotype is outdated — modern MongoDB gives you most relational guarantees, if you opt in.

lecture09 / embed-vs-reference
the single most important MongoDB decision

Embed vs. Reference

embed (denormalize)
{
  name: "Alice",
  addresses: [
    { street: "123 Main", city: "Toronto" },
    { street: "456 Oak", city: "Vancouver" }
  ]
}
reference (normalize)
{ name: "Alice", companyId: ObjectId("...") }

// separate company document
{ _id: ObjectId("..."), name: "Google" }
  • Data read together → embed
  • One-to-few relationship → embed
  • Data changes independently → reference
  • One-to-many / many-to-many → reference

Schema Design Decision Guide

QuestionIf YesIf No
Is the data always accessed together?EmbedReference
Is it a one-to-few relationship?EmbedReference
Does the child data change frequently?ReferenceEmbed
Can the embedded array grow unbounded?ReferenceEmbed
Do you need to query the child independently?ReferenceEmbed
There is no perfect answer — schema design is always a trade-off between read performance and write complexity.

Mongoose Schema Validation

validation.js — required, format
const userSchema = new Schema({
  name: {
    type: String,
    required: [true, 'Name is required'],
    trim: true,
    minlength: [2, 'min 2 characters'],
  },
  email: {
    type: String,
    required: true, unique: true,
    match: [/^\S+@\S+\.\S+$/, 'invalid email'],
  },
validation.js — range, enum
  age: {
    type: Number,
    min: [0, 'cannot be negative'],
    max: [150, 'seems unrealistic'],
  },
  role: {
    type: String,
    enum: ['user', 'admin', 'moderator'],
    default: 'user',
  },
});
Validate at the schema level — don't rely on frontend validation alone. A malicious or buggy client can always send a raw request.
