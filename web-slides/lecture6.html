What Is TypeScript?

  • TypeScript is a superset of JavaScript — every valid JS file is already valid TS
  • It's a strongly typed language layered on top of JS's dynamic types
  • It compiles ("transpiles") down to plain JavaScript — browsers and Node never see TS directly
Types are erased at compile time — they exist only to help you and your tools, never at runtime.

lecture06 / tsconfig-why
every option, justified

tsconfig.json — Why These Options?

  • target / module — match your runtime (Node 18+ can use ES2022; CommonJS for many Node backends)
  • rootDir / outDir — keep TS source and compiled JS output cleanly separated
  • sourceMap — enables debugging the original TS in your IDE and Node inspector
  • the strict family — catch more bugs at compile time; enable by default, dial back only if needed
  • esModuleInterop — smooth interop when importing CommonJS packages
  • skipLibCheck — speeds up builds; keep it on unless debugging a type package itself
Tip: sample_code/lecture6/tsconfig.json exists — compare and evolve it toward this when building a real app or service.

lecture06 / discriminated-union
a tag TS can switch on

Discriminated Union

  • Give every variant of a union a shared, literal tag field (often called kind)
  • Once you check the tag, TypeScript narrows the whole object automatically
  • This pattern comes back later for typed service results
discriminated-union.ts
interface Shape {
  kind: 'circle' | 'square';
  radius?: number;
  sideLength?: number;
}

function area(s: Shape): number {
  if (s.kind === 'square') {
    return s.sideLength! ** 2;
  }
  return Math.PI * s.radius! ** 2;
}

Narrowing a Real Union

A query param can legitimately arrive as string | string[] | null — narrow it before using it.

type-guard.ts
function prettyPrint(strs: string | string[] | null) {
  if (strs === null) {
    console.log('null');
  } else if (typeof strs === 'string') {
    console.log(strs);                // TS knows: string
  } else {
    console.log(strs.join(' + '));  // TS knows: string[]
  }
}
Array.isArray(x) narrows the same way — the array vs. object equivalent of typeof.

lecture06 / user-defined-guards
arg is Type

User-Defined Type Guards

  • A function can tell the compiler how to narrow, via an arg is Type return type
  • Runs like an ordinary boolean check — but TS remembers the result afterward
  • Use this at boundaries (API responses, unknown input) to convert loose data into your domain types
assignments.ts
type Dog = { bark: () => void };
type Cat = { meow: () => void };

function isDog(pet: Dog | Cat): pet is Dog {
  return (pet as Dog).bark !== undefined;
}

if (isDog(pet)) pet.bark();   // TS knows: Dog
else pet.meow();              // TS knows: Cat

Optional & Default Parameters

optional — ?
function log(
  message: string,
  userId?: string
): void {
  console.log(
    message, userId || 'Not signed in'

  message = 'logging',
  userId?: string
): void {
  console.log(
    message, userId || 'Not signed in'
  );
}
Optional params must come after required ones. A default value also makes a parameter optional — and infers its type from the default.

Function Overloading

  • Declare several call signatures for the same function name, then one implementation that handles them all
  • The implementation signature itself is not visible to callers
  • Function overloading is not supported in plain JavaScript
overloading.ts
function len(s: string): number;
function len(arr: any[]): number;
function len(x: any): number {
  return x.length;
}

len('hello');       // ✅ matches signature 1
len([0, 1, 2]);   // ✅ matches signature 2

lecture06 / writing-good-generics
seven guidelines

Guidance for Writing Generics

  • 1. Use multiple type params to describe all of a function's argument types
  • 2. Use extends to constrain type parameters
  • 3. Use keyof to describe index types
  • 4. Use mapped types to describe generic objects
  • 5. Use type params to relate arguments to each other
  • 6. Use type params to relate return types to arguments
  • 7. Use type params to describe callback shapes
generics.ts
// #2 + #3: constrain with extends + keyof
function getProperty<T, K extends keyof T>(
  obj: T, key: K
) {
  return obj[key];
}

const user = { name: 'John', age: 30 };
getProperty(user, 'name');  // ✅
getProperty(user, 'email'); // ❌ not a key of user

lecture06 / shaping-dtos

Shaping DTOs

Start from one domain type, then derive request-shaped types from it — don't hand-write them separately, or they'll drift out of sync.

user.ts · user.dtos.ts
interface User {
  id: string; email: string; name: string;
  passwordHash: string; createdAt: Date;
}

// Create: exclude server-generated fields, require a raw password
type CreateUserDto = Omit<User, 'id' | 'createdAt' | 'passwordHash'> & {
  password: string;
};

// Update: require the id, allow everything else partial
type UpdateUserDto = Pick<User, 'id'> &
  Partial<Omit<User, 'passwordHash' | 'createdAt'>>;

lecture06 / typed-outcomes
real-world pattern

Typed Outcomes

Recall Discriminated Union from Part 1 — the same kind pattern models a function's outcome, so callers can't forget to handle a case.

service-result.ts
interface Ok<T>    { kind: 'ok'; data: T }
interface NotFound { kind: 'not_found'; message: string }
interface Failure  { kind: 'error'; error: Error; code?: string }

type ServiceResult<T> = Ok<T> | NotFound | Failure;
No null returns, no thrown exceptions for expected failures — the type itself lists every possible outcome.

Service → Controller

user.service.ts
class UserService {
  async create(dto: CreateUserDto):
    Promise<ServiceResult<User>> {
    const user: User = {
      id: 'u_123', email: dto.email,
      name: dto.name, passwordHash: 'hashed',
      createdAt: new Date()
    };
    return { kind: 'ok', data: user };
  }
}
user.controller.ts
// switch on `kind` — TS verifies every case is handled
switch (result.kind) {
  case 'ok':
    return { status: 201, body: result.data };
  case 'not_found':
    return { status: 404, body: { error: result.message } };
  case 'error':
    return { status: 500, body: { error: result.error.message } };
  default: {
    // ← compile error if a `kind` is ever missed
    const _exhaustive: never = result;
    return _exhaustive;
  }
}
That never is the same never from the type list — the compiler proves the switch is exhaustive.
