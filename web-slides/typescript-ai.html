Why This Lecture Exists

TypeScript has become the dominant language for applied AI product development — not because AI needs TypeScript, but because AI output is fundamentally untyped, and TypeScript is how you build a safe boundary around it.

  • An LLM's response is a string. Always. Even "structured output" is a string that looks like JSON.
  • Every layer of a real AI product — API calls, tool calling, agents, MCP — is really the same question asked again: how do I trust data I didn't generate myself?
  • This lecture is about that one recurring problem, seen from four angles.

Where TypeScript Actually Sits

TypeScript does not make an LLM's output correct. It makes exactly one thing true everywhere in this path:

Nothing downstream can accidentally treat unchecked data as trusted data.
  • unknown (not any) is the honest type for "a model produced this"
  • A schema (zod) is the single place that decides what "valid" means
  • A type (z.infer) is derived from that schema — never hand-written separately, or the two drift apart
  • Every section ahead applies this same pattern at a different boundary: HTTP response, stream chunk, tool call, MCP request

The Problem: A String Is Not a Type

problem.ts
// What an LLM call actually returns — always, no matter what
// the SDK's TypeScript types claim about the "structured" response.
const raw: string = await callModel(prompt);

const parsed = JSON.parse(raw); // `any`. Could be anything. Could throw.
parsed.rating.toFixed(1);  // compiles. crashes if rating is a string,
                          // or missing, or the model added an extra field.
  • TypeScript can't help here — JSON.parse returns any by design
  • The type system was bypassed the moment untyped JSON entered the program
  • True whether the JSON came from an LLM, a webhook, or req.body — same problem, different source

The Fix: Schema First, Type Derived

reeltalk-api/src/schema/movieSummary.ts
movieSummary.ts
import { z } from 'zod';
export const MovieSummarySchema = z.object({
  rating: z.number().min(1).max(5),
  verdict: z.string().min(1),
  tags: z.array(z.string()).min(1).max(5),
});
// INFERRED, not hand-written — one source of truth, not two
export type MovieSummary = z.infer<typeof MovieSummarySchema>;
  • The schema is runtime code (it actually validates) and a compile-time type via z.infer — a hand-written interface is only the second half
  • .min() / .max() encode business rules a bare TS interface cannot express at all

The Fix: Validate at the Boundary

reeltalk-api/src/summarySSE.ts
summarySSE.ts
// buildRawSummary() returns `unknown` — untrusted, on purpose
function buildRawSummary(movie: Movie): unknown { /* ... */ }
const parsed = MovieSummarySchema.safeParse(buildRawSummary(movie));
if (!parsed.success) {
  res.status(500).json({ message: 'AI summary failed validation' });
  return;
}
const summary: MovieSummary = parsed.data; // ← now, and only now, trusted
  • safeParse never throws — it returns a result you branch on, so a malformed generation degrades gracefully instead of crashing the process
  • unknown is the type that forces this check to exist; any would have let the bug ship

A Discriminated Union for Stream State

reeltalk/src/hooks/useAiSummary.ts
useAiSummary.ts
export type AiSummaryState =
  | { status: 'idle' }
  | { status: 'streaming'; verdict: string }
  | { status: 'done'; verdict: string; rating: number; tags: string[] }
  | { status: 'error'; message: string };
  • status is the discriminant — the same pattern as lecture6's ServiceResult<T>, applied to a stream instead of a function return
  • state.rating is only accessible once state.status === 'done' narrows the union — reading it while 'streaming' is a compile error, not a runtime undefined

source.addEventListener('done', (event) => {
  let raw: unknown;
  try { raw = JSON.parse(event.data); }
  catch {
    return setState({ status: 'error', message: 'Malformed summary payload' });
  }
  const parsed = MovieSummaryTailSchema.safeParse(raw);
  if (!parsed.success) {
    return setState({ status: 'error', message: 'Summary failed shape validation' });
  }
  setState({ status: 'done', verdict: prev.verdict, ...parsed.data });
});
  • The client re-validates — it does not trust "the server already checked this." The network is a trust boundary in both directions.

What "Tool Calling" Actually Is

  • You describe a function to the model: a name, a description, and a schema for its arguments
  • The model decides to call it, and produces arguments matching that schema — as text, that your code must parse and validate
  • Nothing stops a model from producing malformed or "creatively reinterpreted" arguments — it is guessing at your contract, not executing your code directly
flow
model reads tool description → model emits arguments (JSON text)
        → YOUR CODE validates → YOUR CODE executes the handler
Executing model-provided arguments without checking them is the same class of bug as eval()-ing user input.

The Same zod Pattern, One Layer Up

searchMovies.ts
// The tool's argument schema — the model's "function signature"
const SearchMoviesInput = z.object({
  genre: z.enum(['drama', 'sci-fi', 'comedy', 'horror']),
  minRating: z.number().min(0).max(5).default(0),
});

async function searchMoviesHandler(rawArgs: unknown) {
  const args = SearchMoviesInput.parse(rawArgs); // throws on bad input, by design
  return movies.filter((m) => m.genre === args.genre && m.averageRating >= args.minRating);
}
  • Same schema → derive-a-type → validate-before-use pattern as the AI summary — the boundary moved, the technique didn't
  • This is exactly what sample_code/typescript-ai/mcp-movie-tool does, generalized to a protocol (next section)

MCP Is Tool Calling Across a Process Boundary

  • Tool calling (previous section) works when the tool is a function in the same process as your app
  • MCP (Model Context Protocol) standardizes that same contract so tools can live in a separate process — a different language, a different machine, a shared ecosystem of agents and tools
  • The official @modelcontextprotocol/sdk is TypeScript-first — not a coincidence, given everything so far in this lecture
mcp-flow
Agent (Claude, etc.) ⇄ MCP protocol ⇄ your MCP server ⇄ your handler
                        ^^^^^^^^^^^^
                same trust boundary as tool calling — now also crossing a process/machine boundary

Modeling Failure, Not Just Success

useAiSummary.ts
export type AiSummaryState =
  | { status: 'idle' }
  | { status: 'streaming'; verdict: string }
  | { status: 'done'; verdict: string; rating: number; tags: string[] }
  | { status: 'error'; message: string };
  • Rate limits, refused answers, malformed generations, dropped connections — a real AI feature has more failure modes than a typical CRUD call, not fewer
  • A discriminated union forces every consumer to handle 'error' — there's no try { data.rating } escape hatch that silently ships undefined to a template

Choosing Where to Put the Boundary

SituationPut the schema at
Calling an LLM directly for structured outputThe response parser, before app code touches it
Exposing a function the model can callThe tool's argument schema
Exposing a tool across processesThe MCP inputSchema / outputSchema
Streaming a result to the UIEach chunk type, via a discriminated union
One rule underneath all four rows: validate at the edge, trust in the middle. Once data has passed a schema, let the type system do the rest — don't re-check the same value five call-stacks later "just in case."

Lecture Summary

demo: reeltalk + reeltalk-api + mcp-movie-tool
  • The AI product path: prompt → structured output → tool calling → MCP → production — the same "untyped in, typed out" problem at every step
  • zod: schema as the single source of truth; the type is z.infer'd, never hand-written separately
  • Typed streaming: discriminated unions for stream state, re-validated on arrival
  • Tool calling & MCP: model-provided arguments are guesses at your contract — validate before running, in-process or across one
  • The ecosystem: OpenAI, Anthropic, and Vercel AI SDK all repeat this same pattern
