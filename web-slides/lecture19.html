Where We Are: Everything Has Been CSR

Every app built in this course — PodWave, StreakUp, ReelTalk's frontend — renders entirely in the browser:

csr-flow
Server sends: <div id="root"></div> + a JS bundle
Browser runs the JS bundle → React renders everything → page appears
  • First paint waits for: download JS → parse/execute JS → fetch data → render
  • Search crawlers and link previews see an empty <div> unless they execute JS
  • Fine for logged-in dashboards, internal tools — not for public, content-heavy pages

Hand-Writing SSR: The Server Side

reeltalk-ssr/src/server.js
server.js
import { renderToPipeableStream } from 'react-dom/server';
app.get('/movies/:id', async (req, res) => {
  const movie = await fetchMovie(req.params.id);   // plain fetch() to GraphQL
  const { pipe } = renderToPipeableStream(<Document movie={movie} />, {
    bootstrapScripts: ['/client.js'],
    onShellReady() {
      res.setHeader('Content-Type', 'text/html');
      pipe(res);                                  // stream HTML directly
    },
  });
});
Data is fetched before rendering. renderToPipeableStream streams HTML chunks as ready. The real file uses createElement(...) instead of JSX — no build step, no compiler. Same output either way.

Handing Data to the Client: __INITIAL_DATA__

reeltalk-ssr/src/server.js, client.js

server.js — embed what we already have

server.js
h('script', {
  dangerouslySetInnerHTML: {
    __html: `window.__INITIAL_DATA__ =
      ${JSON.stringify(movie)};`,
  },
})

client.js — read it instead of fetching

client.js
const movie = window.__INITIAL_DATA__;
hydrateRoot(
  document.getElementById('root'),
  <MovieDetailView movie={movie} />
);
This hand-off IS the main SSR tax: fetch once on the server, serialize it, ship it, deserialize it again on the client. RSC's whole pitch is removing this step entirely.

The Hydration Mismatch Trap

The contract: server and client must render the exact same output from the exact same props.

Greeting.jsx
// ❌ Different output between server and client render
function Greeting() {
  return <p>Rendered at {new Date().toLocaleTimeString()}</p>;
  // Server renders this at request time. Client re-evaluates it
  // at hydration time — a few hundred ms later. Different string.
}
React detects the mismatch, logs a warning, and throws away the server-rendered DOM, re-rendering from scratch — silently defeating the point of SSR. Common causes: Date.now()/Math.random() during render, typeof window !== 'undefined' branches, locale/timezone differences.

Enter React Server Components

RSC is a third kind of component, alongside server-rendered-then-hydrated and pure client components:

MovieDetailPage.jsx
// A Server Component — this is NOT what reeltalk-ssr does
async function MovieDetailPage({ id }) {
  const movie = await fetchMovie(id);   // await, directly, in the component
  return <div>
    <h1>{movie.title}</h1>
    <ReviewForm movieId={movie.id} />  {/* a Client Component */}
  </div>;
}
No useEffect, no loading state, no __INITIAL_DATA__ hand-off — the component just awaits. This code — including the data-fetching logic — never ships to the browser at all.

'use client': Drawing the Boundary

ReviewForm.jsx
'use client';   // <-- everything below runs on the CLIENT

import { useState } from 'react';

export function ReviewForm({ movieId }) {
  const [body, setBody] = useState('');   // Server Components CAN'T do this
  // ...
}
  • Server Components (the default): can be async, read files/DBs/APIs directly, cannot use useState, useEffect, or event handlers
  • Client Components ('use client'): everything you already know — hooks, interactivity, browser APIs
  • A Server Component can render a Client Component — it just can't hold state or handle events itself

RSC vs. Hand-Written SSR: What It Saves

Compare to reeltalk-ssr/src/server.js + client.js
Hand-written SSR (reeltalk-ssr)RSC (Next.js App Router, conceptual)
Data fetchingServer fetches, serializes into __INITIAL_DATA__Component awaits directly
Client bundleShips MovieDetailView + hydration codeShips ONLY the Client Component subtree
HydrationFull component tree re-attachesOnly Client Component "islands" hydrate
Extra step to avoid re-fetchYes — the __INITIAL_DATA__ hand-offNo — data never left the server
Not a "RSC is strictly better" slide — RSC requires a framework implementing the RSC protocol (Next.js App Router, and few others). reeltalk-ssr shows you the mechanism your framework is automating.

Why Runtime CSS-in-JS and RSC Don't Mix Well

Button.jsx
// A typical runtime CSS-in-JS component
const Button = styled.button`
  background: ${(props) => props.theme.accent};
`;
  • styled-components and similar libraries inject <style> tags using JS that runs in the browser, often reading a ThemeProvider from Context spanning the whole tree
  • A Server Component has no client-side JS runtime to run that injection code, and can't participate in Context crossing the server/client boundary
  • Not a hard rule ("CSS-in-JS is banned") — libraries are evolving compile-time-only variants — but it's why zero-runtime approaches have gained ground alongside RSC

CSS Modules in Practice

reeltalk/src/components/MovieList.jsx, MovieList.module.css
MovieList.module.css
.card { display: flex; gap: var(--space-2); }
.active { background: var(--color-accent-soft); }
MovieList.jsx
import styles from './MovieList.module.css';

<li className={movie.id === selectedMovieId
  ? `${styles.card} ${styles.active}`
  : styles.card}>
  • Each .module.css file's classnames are scoped to that file at build time — styles.card might compile to _card_a8f3k1, guaranteed unique
  • No extra library needed to combine classnames conditionally — they're just strings
  • Zero JavaScript runtime cost — the CSS ships as a normal .css file

Design Tokens: Naming the Design System

reeltalk/src/styles/tokens.css
tokens.css
:root {
  --color-bg: #0b0b12;
  --color-accent: #e0b34c;
  --space-2: 0.5rem;
  --radius-md: 8px;
}
  • A design token is a named value (--color-accent, not #e0b34c scattered across 15 files) — change it once, every component updates
  • CSS custom properties (var(--...)) are the mechanism here; the same concept exists in Tailwind config, Style Dictionary, or CSS-in-JS theme objects — the naming discipline matters more than the tool
