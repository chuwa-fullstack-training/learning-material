What Is Multi-tasking?

Multi-tasking is the ability to run multiple tasks at the same time. Most languages achieve it one of two ways:

  • Multi-threading — spin up OS-level threads (Java, Python, Go…)
  • Event loop — a single thread that never blocks, and cycles through queued work (JavaScript)
Java — thread pool
ExecutorService executor =
  Executors.newFixedThreadPool(2);
executor.submit(() -> {
  System.out.println(
    "Async task in Java");
});
Python — asyncio (event loop)
import asyncio

async def main():
  print("Start")
  await asyncio.sleep(2)
  print("End")

asyncio.run(main())
JavaScript picked the event loop model from day one — no threads to manage, no locks, no race conditions on shared memory.

Threads vs Processes

🏭 Process

An instance of a running program. Has its own memory space — code, heap, data segment. The unit the OS allocates resources to.

👷 Thread

A sequence of instructions inside a process, executed independently. The unit the CPU actually schedules. One process can have many threads.

Analogy: a process is a factory; threads are the workers inside it. Workers (threads) share the factory floor (memory), but each factory (process) gets its own building.

Browser Multi-Process Architecture

In Chrome, each tab is (usually) its own process. Inside every process, work is further split across dedicated threads.

🧭 Browser

The coordinator. Address bar, bookmarks, network access, talks to every other process.

🖼 Renderer

One per tab. Runs HTML/CSS/JS — main thread + IO thread live here.

🎨 GPU

Handles compositing and rasterization — shared across all tabs.

🌐 Network

Fetches resources over the wire, independent of any single tab.

🎯 This is why one crashed tab doesn't take down your whole browser — each tab's renderer is an isolated process.

How JavaScript Works

  • JavaScript is single-threaded — one V8 instance runs on the main thread
  • This simplifies everything: no locks, no shared-memory races
  • Almost all your code runs on that one main thread
  • Exception: Web Workers — a real background thread, with no shared memory access
  • Concurrency ≠ Parallelism

Concurrency vs Parallelism

Concurrency — juggling many tasks by switching between them (what the event loop does).

Parallelism — actually running tasks at the exact same instant on separate cores (what threads/Workers do).

A Function Can Run Twice, Two Ways

The same function can be called directly (synchronous) or handed to the browser as a callback (asynchronous, fires later on click).

  • logger() runs immediately, synchronously
  • button.addEventListener(...) just registers — it runs whenever (and if) the button is clicked
sync-async.js
function logger() {
  console.log('log');
}

// registered — runs LATER, on click
button.addEventListener('click', logger);

// called directly — runs NOW
logger();  // 'log' (immediately)

Timers

Timers schedule a callback to run no earlier than N milliseconds from now — the Web API queues it as a macrotask once the timer expires.

setTimeout — once

once
setTimeout(() => {
  console.log('Hello');
}, 1000);

setInterval — repeating

repeating
let id = setInterval(() => {
  console.log('Hello');
}, 1000);

clearInterval(id);  // stop it
"1000ms" is a minimum, not a guarantee. If the call stack is busy, the callback waits until the stack clears — even past its delay.

Callback Hell

  • Occurs when too many callbacks nest inside each other
  • Code drifts right, becomes hard to read and maintain

Promises: Three States

A Promise is an object representing the eventual result of an async operation. It's created once, and settles exactly once.

Fulfilled or Rejected = Settled — once settled, a Promise's outcome never changes again.

Create & Chain Promises

promise-creation.js
const promise = new Promise((resolve, reject) => {
  if (/* success */) {
    resolve(/* value */);
  } else {
    reject(/* reason */);
  }
});
chaining — result flows down
fetch('https://api.github.com/users')
  .then(response => response.json())
  .then(data => console.log(data));

// each .then() passes its return value
// to the NEXT .then() in the chain
If a .then() returns a value, the next .then() gets it directly. If it returns another Promise, the chain waits for that one to settle first.

Promises in Parallel

Promise.all()

Waits for every promise. One rejection = it rejects immediately.

Promise.race()

Settles as soon as the first promise settles — win or lose.

Promise.allSettled()

Waits for all, regardless of outcome. Never rejects.

promise-parallel.js
const promises = [fetch('/api/users'), fetch('/api/posts'), fetch('/api/comments')];
const results = await Promise.allSettled(promises);
results.forEach((r, i) => { if (r.status === 'rejected') console.log(`Request ${i} failed`, r.reason); });

async / await

async/await is sugar on top of Promises — it makes asynchronous code read like synchronous code, top to bottom.

  • An async function always returns a Promise
  • await pauses the function until that Promise settles
  • It doesn't block the whole thread — only this function waits
async-await.js
// Promise chain
function getUser(id) {
  return fetch(`/api/users/${id}`)
    .then(res => res.json());
}

// same thing, async/await
async function getUser(id) {
  const res = await fetch(`/api/users/${id}`);
  return res.json();
}

Error Handling

Bugs happen. try/catch lets you handle them gracefully around await calls instead of crashing the app.

  • Every JS Error object has:
  • name — the error type (e.g. TypeError)
  • message — human-readable description
  • stack — the call trace at throw time
try-catch.js
async function fetchUser(id) {
  try {
    const res = await fetch(`/api/users/${id}`);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();
  } catch (error) {
    console.error(error.message);
    return null;  // graceful fallback
  }
}

Before & After: Adding a Promise

Only sync + setTimeout
no promise
console.log('start');
setTimeout(() => {
  console.log('setTimeout');
}, 0);
console.log('end');
Output: start → end → setTimeout
+ a microtask in the mix
with promise
console.log('start');
setTimeout(() => {
  console.log('setTimeout');
}, 0);
Promise.resolve().then(() => {
  console.log('Promise');
});
console.log('end');
Output: start → end → Promise → setTimeout
The microtask (Promise) always slots in before the macrotask (setTimeout) — even though setTimeout was scheduled first.

Microtasks vs Macrotasks

🟢 Microtask (job)🟣 Macrotask (task)
SourcesPromise.then/catch/finally, queueMicrotasksetTimeout, setInterval, DOM events, I/O, MessageChannel
PriorityRuns before the next macrotask, alwaysRuns one at a time, only once microtasks are drained
Per loop tickALL queued microtasks runExactly ONE queued macrotask runs
DangerA microtask that queues another microtask can starve macrotasks (rendering, input)—
Further reading: Jake Archibald — "Tasks, microtasks, queues and schedules" (jakearchibald.com).

async/await Error Patterns

Pattern 1 — try/catch

most common
async function fetchUser(id) {
  try {
    const res = await fetch(`/api/users/${id}`);
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return await res.json();
  } catch (error) {
    console.error(error.message);
    return null;
  }
}

Pattern 2 — wrapper (Go-style)

reusable
async function tryCatch(promise) {
  try {
    const data = await promise;
    return [data, null];
  } catch (error) {
    return [null, error];
  }
}

const [user, err] = await tryCatch(fetchUser(1));

Promise.all vs allSettled

promise-parallel.js
const promises = [
  fetch('/api/users'),     // ✅ succeeds
  fetch('/api/posts'),     // ❌ fails (404)
  fetch('/api/comments'),  // ✅ succeeds
];

const all = await Promise.all(promises);          // ❌ throws! one failure = all fail
const settled = await Promise.allSettled(promises);  // waits for ALL regardless
🎯 Real-world case: a dashboard loading multiple APIs. allSettled lets successful widgets render normally while failed ones show their own error state — instead of the whole page breaking.

🔁 Execution Model

📈 The Evolution

  • try/catch around await
  • Choose all vs allSettled deliberately
