The Motivating Question

Why does an AI chatbot's reply appear one word at a time?

  • The full answer takes several seconds to generate. Waiting for all of it, then showing it at once, feels broken.
  • So the server sends each token as it's produced, over a single long-lived HTTP response that stays open.
  • That's Server-Sent Events — and it's why SSE went from niche to everywhere once LLM chat UIs became common.
This lecture is about the transports underneath that experience — and they connect back to what you already built: L18's GraphQL Subscription was one such real-time transport, riding on the next one we'll cover.

Server-Sent Events: The Server Side

reeltalk-api/src/summarySSE.js
summarySSE.js
app.get('/movies/:id/summary', (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream');  // <- makes it SSE
  res.setHeader('Cache-Control', 'no-cache');
  res.setHeader('Connection', 'keep-alive');
  const tokens = buildSummary(movie).split(' '); let i = 0;
  const interval = setInterval(() => {
    if (i < tokens.length) res.write(`data: ${tokens[i++]}\n\n`);  // <- SSE wire format
    else { res.write('event: done\ndata: end\n\n'); clearInterval(interval); res.end(); }  // <- named event
  }, 80);
  req.on('close', () => clearInterval(interval)); // client left mid-stream
});
text/event-stream is what makes the browser treat this as a stream — each message is data: payload\n\n, and the blank line is the delimiter. The response stays open; you res.write() repeatedly instead of res.json() once. No real LLM here — the lesson is the transport, not the text.

Server-Sent Events: The Client Side

reeltalk/src/hooks/useAiSummary.js
useAiSummary.js
const source = new EventSource(`${API_BASE}/movies/${id}/summary`);
source.onmessage = (event) => {
  setText((prev) => prev + ' ' + event.data);   // append each token
};
source.addEventListener('done', () => source.close()); // else it auto-reconnects!
source.onerror = () => source.close();
  • EventSource is the browser's built-in SSE client — it even auto-reconnects if the connection drops.
  • Key limitation: it can only make GET requests — no custom headers, no body. Fine here, since the id is in the URL.
  • Need to POST a prompt to an LLM? Use fetch() + a ReadableStream reader instead — same wire format, more control.

Raw WebSocket: Rebuilding L18's Live Reviews

reeltalk-api/src/reviewsSocket.js

In L18, "new reviews appear live" used a GraphQL Subscription (useSubscription + graphql-ws). Here's the same feature with a raw ws server — deliberately, to see what that abstraction handled:

reviewsSocket.js
export const reviewsWss = new WebSocketServer({ noServer: true });
reviewsWss.on('connection', (ws, request) => {
  ws.movieId = new URL(request.url, `http://${request.headers.host}`).searchParams.get('movieId'); // ← scope, by hand
});
export function broadcastReview(review) {
  const message = JSON.stringify(review);   // ← serialize by hand
  for (const ws of reviewsWss.clients) {
    if (ws.readyState === ws.OPEN && ws.movieId === review.movieId) ws.send(message); // ← filter, by hand
  }
}
createReview now fires both the GraphQL pubsub.publish (L18, still there) and this broadcastReview. Same event, two transports, so the lecture can compare them live.

Raw WebSocket: The Client Side

reeltalk/src/hooks/useReviewSocket.js
useReviewSocket.js
useEffect(() => {
  const socket = new WebSocket(`${WS_BASE}/ws/reviews?movieId=${movieId}`);

  socket.addEventListener('message', (event) => {
    const review = JSON.parse(event.data);                    // parse by hand
    appendReviewToCache(client.cache, { __typename: 'Review', ...review }); // re-tag by hand
  });

  return () => socket.close();   // clean up by hand
}, [movieId, client]);
  • pass the scope (movieId) as a query-string param — a raw socket has no "arguments"
  • re-attach __typename — forget it and the cache write throws (a real bug hit while building this)

So What Does a GraphQL Subscription Buy You?

Comparing L18's useSubscription to L20's hand-written raw WebSocket, the subscription was quietly handling:

  • Connection & upgrade routing — one socket multiplexed for all subscriptions, path negotiation, reconnection
  • Subscription scope — subscribe(_, { movieId }) args instead of stuffing ?movieId= on a URL
  • Serialization + typing — responses arrive typed and __typename-tagged, ready for the cache
  • Cache integration — results flow into Apollo's normalized cache automatically
This isn't "raw WebSocket is worse." It's "abstractions have a cost and a payoff — now you can see both, and choose deliberately."

Upgrade Routing: One HTTP Server, Two Sockets

reeltalk-api/src/index.js
index.js
const graphqlWss = new WebSocketServer({ noServer: true });
// reviewsWss also { noServer: true }
httpServer.on('upgrade', (request, socket, head) => {
  const { pathname } = new URL(
    request.url, `http://${request.headers.host}`);
  if (pathname === '/graphql')
    graphqlWss.handleUpgrade(...);
  else if (pathname === '/ws/reviews')
    reviewsWss.handleUpgrade(...);
  else socket.destroy();
});
A WebSocket connection starts as an HTTP request with an Upgrade: websocket header. Two { server, path } WebSocketServers on one HTTP server fight over the upgrade event, so we route it ourselves — one more thing graphql-ws normally hides.

Choosing a Transport

Your needReach for
One-directional, server → client (notifications, feeds, AI token streaming)SSE
Two-directional or high-frequency (chat, collaborative editing, multiplayer)WebSocket
Already using GraphQL and just want to push data updatesGraphQL Subscription
Occasional, low-frequency updatesPolling
Defaults matter: SSE is simpler than WebSocket and covers a surprising amount (anything one-way). Reach for a raw WebSocket only when you genuinely need the client → server direction too. And if you're already in GraphQL, a Subscription usually beats hand-rolling either one.

Lecture Summary

  • The spectrum: polling → long-polling → SSE → WebSocket, and what each trades off
  • SSE: text/event-stream, the data:\n\n wire format, EventSource (and its GET-only limit) — the transport behind "AI typing" UIs
  • Raw WebSocket: full-duplex, manual scope/serialization/lifecycle — the same live-review feature L18 got "for free" from a GraphQL Subscription
  • What abstractions cost and buy: seeing the hand-written version makes graphql-ws's conveniences concrete
  • Choosing deliberately: SSE for one-way, WebSocket for two-way, Subscriptions when already in GraphQL, polling when it's enough
