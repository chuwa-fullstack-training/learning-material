Two Common Strategies

A) Cookie + Session (stateful)

  • Browser stores a session id in a cookie
  • Server stores session data (user id, roles, etc.)

B) Token (JWT) (stateless-ish)

  • Client stores a JWT
  • Server verifies the signature and reads claims
Same problem, two different places to keep the "who is this" data — on the server, or inside the token itself.

Cookie Security Flags

HttpOnly

✅ JavaScript cannot read it — mitigates token theft via XSS

Secure

✅ only sent over HTTPS

Scaling Sessions

❌ in-memory session store

Breaks in multi-instance deployments — instance B has never heard of the session instance A created.

✅ shared store

Redis is common — every instance reads/writes the same session data.

Load balancer options: sticky sessions (simpler, less flexible) vs. shared session store (recommended).

Potential Vulnerabilities

XSS

Attacker runs JS in your page → can steal tokens from localStorage / JS-readable cookies.

CSRF

Attacker tricks the browser into sending cookies to your site → possible whenever auth uses cookies.

Session Fixation

Attacker forces a known session id → fixed by regenerating the session after login.

csrf.md
lecture11 / csrf
why cookie auth is vulnerable

CSRF

If the browser auto-sends cookies, a malicious site can trigger:

  • A hidden form submit
  • An image request
  • A fetch request (CORS may block reading the response, but the request can still be sent)
Result: the request reaches your server with valid cookies attached — your server can't tell it apart from a legitimate request.

Pros & Cons: Cookies + Sessions

✅ Pros
  • Easy logout / invalidation (destroy server session)
  • Sensitive data stays on the server
  • Simple mental model for browser apps
❌ Cons
  • Requires a session store (Redis/DB) to scale
  • CSRF concerns (cookie auto-sent)
  • Cookies sent on every request (overhead)
  • Limited for native mobile apps (no browser cookies)

  name: 'sid', secret: process.env.SESSION_SECRET,
  resave: false, saveUninitialized: false,
  cookie: { httpOnly: true, secure: process.env.NODE_ENV === 'production', sameSite: 'lax' }

  req.session.user ? next() : res.status(401).send('Unauthorized');

app.post('/auth/login', (req, res) => {
  const { username, password } = req.body;
  if (valid(username, password)) { req.session.user = { username }; res.send('Logged in'); }
});

app.post('/auth/logout', (req, res) =>
  req.session.destroy(() => { res.clearCookie('sid'); res.json({ ok: true }); }));

app.get('/api/protected', authMiddleware, (req, res) => res.send('Protected data'));

JWT Structure

Header

Algorithm, token type

Payload

Claims — user id, expiration, roles, etc.

Signature

Header + Payload + Secret (or private key)

  • Common claims: sub (subject/user id), exp, iat, iss, aud, plus roles / scope for authorization
⚠️ Put no secrets in the payload. Anyone can decode it.

Where to Store / Send JWT?

Option 1 — Authorization: Bearer <token>
  • ✅ avoids CSRF by default (browser won't auto-attach)
  • ✅ common for APIs / mobile apps
  • ⚠️ vulnerable if stored in localStorage and you have XSS
Option 2 — HttpOnly cookie
  • ✅ mitigates token theft via XSS
  • ⚠️ brings CSRF back (need SameSite + CSRF token)

lecture11 / disadvantages-of-jwt
stateless has a price

Disadvantages of JWT

  • Compromised secret/key: all tokens become forgeable
  • Data visibility: payload is readable (not encrypted)
  • Revocation is harder: needs a strategy (short exp / refresh / denylist)
  • Overhead: larger than a session id cookie
Avoid: putting tokens in URLs — URLs leak via logs, browser history, and referrers.

checklist.md
lecture11 / jwt-implementation-checklist
five things, every time

JWT Implementation Checklist

  • 1. Password storage: never plaintext — bcrypt with salt rounds ≥ 10
  • 2. Token signing: a strong secret (or RS256 key pair in prod)
  • 3. Token expiration: short-lived access tokens (15min–1h) + refresh
  • 4. Middleware: verify on protected routes, attach user to req
  • 5. Error messages: never reveal "user not found" vs "wrong password"
❌ reveals which part is wrong
leaky
if (!user)
  return res.status(401).json({
    error: 'User not found'
  });
✅ generic message
safe
if (!user || !match) {
  return res.status(401).json({
    error: 'Invalid credentials'
  });
}

lecture11 / auth-middleware-pattern

Auth Middleware Pattern

middlewares/auth.js
const jwt = require('jsonwebtoken');

function authMiddleware(req, res, next) {
  const header = req.headers.authorization;
  if (!header?.startsWith('Bearer ')) return res.status(401).json({ error: 'No token provided' });

  try {
    const token = header.split(' ')[1];
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    req.user = decoded;  // attach user info to request
    next();
  } catch (err) {
    res.status(401).json({ error: 'Invalid or expired token' });
  }
}

// usage
app.get('/api/profile', authMiddleware, (req, res) => res.json({ user: req.user }));

when in doubt

Summary (Rules of Thumb)

  • Browser web app: session-cookie is simplest — use secure cookie flags + CSRF protection
  • APIs / mobile / microservices: JWT bearer is common — short expiry + refresh strategy
  • Always implement AuthZ explicitly (roles + resource ownership)
  • Secure defaults:
    • Never put tokens in URLs
    • Avoid storing tokens in localStorage
    • Validate exp/iss/aud and lock down algorithms
